# 界面文字方案的待确认问题

状态：待后续 productivity:grilling 批量确认。本文列出业务选择、影响和有依据的推断；本轮不发起问答或将推荐视为批准。

## Q1：Linux 的文字运行环境由谁维护？

推荐 1：使用 Ubuntu 26.04 提供的 Python/Tk，uv 继续管理项目依赖。

系统负责 Python 3.14、Tk 8.6.17 和 Xft；应用负责依赖锁、启动说明和真实环境验收。用户现有 Ubuntu 目标保留。需要补齐发行版系统包，项目独立 `.venv-linux` 使用系统解释器；锁定数值/OCR 依赖保持不变。TXT-D02 已将此分支完整展开。

选择 2：由应用维护可用的 Python/Tk 运行时，使 Linux 安装更集中。

应用需要负责具有 Xft 能力的 Python/Tk 发行物、构建、依赖库、许可、交付和更新；仍使用系统字体。它能减少对发行版 Python 版本的依赖，同时扩大长期维护与发布范围。当前 uv 携带的实际 Tk 字体能力不能据版本升级直接推断为已修复；私有运行时需要独立实际构建/安装门禁。选择此项后，在最终批准前展开运行时构建与交付原子票，替换 TXT-D02 的范围、Items、ADR 分析和联合门禁。

事实：历史 Linux 探针较强支持当前 uv Tk 走 X core，目标系统字体对它不可见；官方 Ubuntu 26.04 Python/Tk 包及锁定依赖发行文件有支持依据。系统候选尚未实际安装和回归。

推断：对当前单机桌面需求，系统提供运行时可以更少的维护工作达到目标；依据是既有 `.venv-linux` / uv.lock、发行版 Xft Tk 及 CPython 3.14 依赖支持。若要跨发行版统一安装或自行分发解释器，此推断需要重评估。

## Q2：Windows 是否要在不同显示比例的屏幕间拖动时立即保持同等清晰？

推荐 1：支持启动时的显示比例，以及同显示比例的屏幕之间移动。

分别验证 100%、125%、150%、200%，支持窗口放大、缩小、最大化和恢复。系统显示比例调整后重启应用验证；不同 DPI 的屏幕间实时移动不列入这次支持范围。实现采用一次 system-aware 初始化，继续使用当前 View、菜单和 Tk 资源模型。TXT-D03 已完整展开此分支。

选择 2：支持不同显示比例屏幕之间的实时移动，以及运行中比例变化。

玩家可以拖到不同 DPI 的屏幕而保持按新密度绘制。这需要每个顶层窗口独立处理 DPI 变化，并同步 Canvas/Text/Menu/ttk 字体、控件几何、勾选图片、鼠标坐标、工作区和原生弹窗。仅开启 PMv2 标志不能证明这些行为成立。选择此项后，在最终批准前形成该能力的具体接口、资源生命周期、独立票与真实跨屏测试，再替换 TXT-D03/04 及 ADR 草案。它增加支持范围与验证成本，不交由实施 Worker 临场选方案。

事实：Windows 历史探针是 100% / DPI unaware，项目实际 GUI 与其他比例尚未验证。Microsoft 明确区分 system-aware 和 per-monitor 的缩放行为；现有 Tk/View 没有完整动态 DPI 生命周期。

推断：如果主要使用同一个显示比例，system-aware 启动与真实高 DPI 回归可以满足当前已描述的“窗口缩放”需求；依据是窗口尺寸调整与跨屏 DPI 改变属于不同场景。用户是否需要后者无法由当前事实替代裁决。

## Q3：缺失字体名称如何显示，才能便于发现并继续操作？

推荐 1：在主窗口显示可关闭的提示条。

缺失时显示“当前 Tk 未识别首选字体：<名称>。已使用系统回退字体，可继续游戏。”，在普通、提示、暂停和完成页面可见。玩家可关闭，本次运行保持关闭；下次启动重新检测。提示占用棋盘外空间，主窗口最小高度补足提示条高度，保留原 Canvas 最小区域。不弹模态框、不保存配置、不改变 Game 状态。TXT-D01 已完整展开此分支。

选择 2：在设置中提供字体状态入口，玩家主动打开时查看名称。

主窗口保留原空间，玩家需打开设置才能查看缺失名称；系统回退与游戏仍正常使用。最终批准前将入口、只读展示、关闭与资源生命周期，以及普通/Hint/完成页面可达性写入 TXT-D01，替换提示条布局和测试条目。

事实：原业务消息在 Hint/完成页面不提供同一个 status-message 项，且普通重绘会从 Game.message 恢复；把环境提示放入该消息不能满足各页可见与状态隔离。

推断：主窗口提示条更容易让用户及时看到缺失名称；依据是用户明确要求“显示缺失的字体”，而环境状态不应借用游戏消息或打断游戏。展示位置与可见性仍是用户体验选择，因此保留本项裁决。
