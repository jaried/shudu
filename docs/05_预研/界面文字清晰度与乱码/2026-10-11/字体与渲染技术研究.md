# 界面文字清晰度与乱码技术研究

日期：2026-10-11。承接需求：界面文字缩放锯齿与乱码。目标环境：Linux 与 Windows。本文保存研究结论、来源定位和待验证项；原始命令输出与截图由本地核验过程保管。

## 结论

修复需要同时打通三层：**Tk 能使用合适的可缩放字体、按当前尺寸重新绘制字形、桌面以正确的像素密度显示窗口**。字符覆盖另有独立验收。当前 Linux 已定位到 uv 携带的 Tk 字体后端，并确认系统字体与 Tk 可见字体存在差异、字体兜底把 named font 当成 family。修复候选应先保证运行时能使用目标字体，再确定跨平台字体来源与失败处理。

现有应用在窗口变化时重建文字并重新计算字号。源码事实支持“按目标字号重绘”，应用层文字缓存位图放大的原因尚无证据。当前问题也不能仅凭字体文件扩展名解释：轮廓字体最终仍需栅格化，抗锯齿与桌面缩放分别影响最终清晰度。[FreeType 字形加载与渲染](https://freetype.org/freetype2/docs/tutorial/step1.html)、[Fontconfig 字体属性](https://fontconfig.pages.freedesktop.org/fontconfig/fontconfig-user.html)

实际 Linux 桌面的只读核验结果：uv CPython 3.12.15；Tk/Tcl 9.0.4；Tk 的窗口系统为 `x11`，桌面会话为 GNOME Wayland；`tk scaling≈2.666`，Tk 的 `winfo_fpixels('1i')≈191.95`，XWayland 的 `xdpyinfo` 则报告 96 DPI。它们来自不同接口，记录为独立事实。系统 Fontconfig 能匹配 DejaVu Sans 的 TTF 与 Noto Sans CJK SC 的 TTC，均报告 `scalable=True`、`antialias=True`。但 Tk 的 family 列表没有这两个名称，现有两个字体角色都选到 `TkDefaultFont`；作为 family 请求 -28 像素后实际 family 为 `fixed`，实际 size 为 11 点，而单独读取 named font `TkDefaultFont` 的 family 为 `nimbus sans l`。**安装状态、Tk 可见状态与最终选择是三个不同事实。**

加载库已定位为 uv Python 内的 `lib/libtcl9tk9.0.so`；该库符号命中 `ControlUtfProc`、`FindSubFontForChar`、`XListFonts`、`XLoadQueryFont`，同次检索没有 `XftFont` 匹配。Tk 只枚举 45 个传统 family；直接请求 Noto Sans CJK SC 或 DejaVu Sans 也得到 `fixed`。与上游实现对应后，这些结果较强地支持 **当前 uv 携带的 Tk 走 X core 字体路径**。该库还静态打包 Xlib，动态依赖列表本身不足以单独判定后端。系统 `antialias=True` 仅描述 Fontconfig 匹配结果，当前 Tk 使用字体及最终像素需另行观察。

X server 的 `fixed` alias 指向一个 13 像素、字符单元型的 Misc Fixed ISO8859-1 字体，证明当前服务器存在传统字体资源；Tk 在其他请求字号下选用的实际子字体仍需单独对应。

请求 -18、-36、-72 像素时，错误兜底始终选 `fixed`，行距分别为 18、33、68；正确复制 named font 后得到 `nimbus sans l`，行距为 22、42、85。字号确实影响绘制尺寸，字体及可用尺寸受后端约束。可复查结果保存在 Git 外的 `/mnt/d/temp/shudu-font-research-zhLggI/linux-font-probes.json`。

## 字号、named font 与字符覆盖

Tk 的正字号表示点，负字号表示像素；不支持目标字号时允许选择接近尺寸。Canvas 的 `scale` 命令只改变文字的位置，字号需另行设置；本项目已经自行设置字号。因棋盘使用像素逻辑坐标，保留同一比例下的像素字号具备合理依据，实施时需检验实际字形尺寸随窗口变化。[Tk 9.0 font 手册](https://www.tcl-lang.org/man/tcl9.0/TkCmd/font.html)、[Canvas 文本与缩放](https://www.tcl-lang.org/man/tcl9.0/TkCmd/canvas.html)

`TkDefaultFont` 是 named font。单独传该名称使用 named font；`(family, size)` 元组的首项解释为 family。可靠的默认样式路径是读取 named font 属性或复制后修改，再将字体对象提供给控件。Tk 官方建议复制系统 named font 后配置，以保留当前系统样式，再独立配置尺寸。复制对象与原 named font 分别配置，后续系统样式同步需单独设计。[Tk 字体描述与标准字体](https://www.tcl-lang.org/man/tcl9.0/TkCmd/font.html)、[Python 3.12 Font.copy / nametofont](https://docs.python.org/3.12/library/tkinter.font.html)

本次实际 UI 字符集合应覆盖中文、0–9、英文算法与快捷键、全角标点，以及 `▶` U+25B6、`…` U+2026、`·` U+00B7、`–` U+2013、弯引号 U+201C/U+201D。可见入口包括正常、暂停、完成、提示、关卡菜单、设置、帮助、导入及保存失败弹窗。设置勾选目前为 PhotoImage 绘制，已核对的 GUI 文案没有非 BMP 图形符号；控制台的 `✓`、`⚠` 属于独立输出路径。

应按以下可观察结果分流：

| 现象 | 定位动作与判断条件 |
| --- | --- |
| 文本值已变成错误字符或 U+FFFD | 比对源字符串与 Tk 控件读回的 Unicode 码点，再定位发生变化的读入/转换层；已核对的 GUI 静态文案直接使用 Unicode 字符串，尚未发现其编码损坏证据 |
| 文本值正确，屏幕缺字或出现转义 | 查询 `font actual … -- char` 的逐字符实际 family，并检查字形覆盖；该查询帮助定位回退，单靠 family 或非零宽度仍不足以证明正确字形 |
| 文字正确但边缘粗糙 | 分别检验字体可缩放性、当前字体后端抗锯齿、窗口表面的系统缩放；比较相同字符在相同像素字号下的实际绘制 |

Tk 提供逐字符实际字体查询，且允许使用另一字体绘制基础字体缺少的字符。Xft 实现按 Fontconfig 排序的字体集合和 charset 查找；X core 实现在全部回退缺失后可把字符转成字面 `\uXXXX` 绘制，因此缺字转义是一个可验证分支。当前测试字符与字面六字符转义的宽度并不相等；原乱码位置缺少具体字符与实际画面，原因保持待定位。[Tk font actual](https://www.tcl-lang.org/man/tcl9.0/TkCmd/font.html)、[Tk 9.0.4 Xft GetFont / InitFont](https://raw.githubusercontent.com/tcltk/tk/core-9-0-4/unix/tkUnixRFont.c)、[X core FindSubFontForChar / ControlUtfProc](https://raw.githubusercontent.com/tcltk/tk/core-9-0-4/unix/tkUnixFont.c)

## Linux 与 Windows 的能力边界

Linux 的 Tk 构建在 Xft 可用时编译 `tkUnixRFont.o`；关闭或检测失败时编译 `tkUnixFont.o`。Xft 路径使用 Fontconfig/FreeType，支持可缩放字体及抗锯齿；X core 也能使用部分可缩放字体，但缺少 Xft 的抗锯齿能力。Tk 版本号与系统安装字体都不能替代后端能力核验。[Tk 9.0.4 构建配置](https://raw.githubusercontent.com/tcltk/tk/core-9-0-4/unix/configure.ac)、[X.org 字体系统说明](https://xorg.freedesktop.org/archive/X11R7.6/doc/xorg-docs/fonts/fonts.html)

Fontconfig 的 `outline/scalable`、`charset` 与 `antialias` 分别表达轮廓/可缩放性、编码字符覆盖和绘制配置。FreeType 可以把同一轮廓字形绘成灰度抗锯齿或单色位图，部分字体还带有特定字号的嵌入位图。因此“轮廓字体”与“平滑显示”需要分别验证。[Fontconfig 属性](https://fontconfig.pages.freedesktop.org/fontconfig/fontconfig-user.html)、[FreeType 渲染模式](https://freetype.org/freetype2/docs/tutorial/step1.html)

当前桌面已启用 `scale-monitor-framebuffer` 与 `xwayland-native-scaling`。GNOME 官方说明后者改进传统 X11 应用的分数缩放；当前存在该配置，仍需逐屏核验表面像素尺寸与物理显示比例。后端抗锯齿和合成器重采样是不同层，不能用调整 Tk 点/像素换算替代该检查。[GNOME 47 分数缩放说明](https://release.gnome.org/47/)

上游 Tk 9.0.4 的 Windows 实现使用 GDI `CreateFontIndirectW`，字体质量为 `DEFAULT_QUALITY`；Microsoft 说明这种质量设置下，平滑行为受系统 `SPI_GETFONTSMOOTHING` 设置影响。Tk 通用 `-font` 参数没有独立的抗锯齿开关。[Tk Windows GetScreenFont](https://raw.githubusercontent.com/tcltk/tk/core-9-0-4/win/tkWinFont.c)、[Microsoft 字体质量参数](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-createfontw)

Windows 的 DPI unaware 进程会被系统整体拉伸；system aware 进程在不同 DPI 显示器之间移动时也可能被拉伸。Per-monitor 模式要求应用处理 DPI 变化。实际 Python/Tk 进程的感知模式、字体覆盖、窗口重绘与跨屏表现需要在真实 Windows 上核验；运行时版本与声明 DPI aware 都不足以单独证明清晰度。[Microsoft 桌面高 DPI 模式](https://learn.microsoft.com/en-us/windows/win32/hidpi/high-dpi-desktop-application-development-on-windows)

## 可选路线与后续验证

| 路线 | 所需决策与验证 |
| --- | --- |
| 原生 Tk 运行时与字体选择修复 | 明确 Linux Xft 能力与 Windows 平滑/DPI 的支持基线；校正 named font 使用，统一棋盘、提示与菜单的字体角色。当前证据优先支持调查此路线，效果须通过两平台实际页面证明 |
| 应用携带固定字体资产 | 决定字体、许可、体积与支持字符集合；Linux 可使用 Fontconfig 的应用字体注册，Windows 可用 `FR_PRIVATE` 注册。随后验证 Tk 可见性、回退、字体资源生命周期。注册字体本身不能补齐当前 Tk 的 Xft 能力 |
| 改变文字绘制后端 | 在原生路线无法达到获批支持基线时评估；需要覆盖 Canvas、Text、ttk、菜单、选取和可访问性，并重新评估模块边界、依赖、性能与资源成本 |

第二条路线的一手依据：[Fontconfig 应用字体](https://fontconfig.pages.freedesktop.org/fontconfig/fontconfig-devel/#FcConfigAppFontAddFile)、[Windows AddFontResourceExW](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-addfontresourceexw)。Noto Sans CJK 提供中文区域资源，其具体资产及许可可从[官方分发指南](https://github.com/notofonts/noto-cjk/blob/main/Sans/README.md)和[许可证](https://raw.githubusercontent.com/notofonts/noto-cjk/main/Sans/LICENSE)核对；目前尚未选定资产。

实施设计继续遵循 ADR-002 的 Hint→View 绘制 Interface、ADR-005 的 Tk 菜单 Module 与增量消息执行面。字体规则若集中成 Module，其 owner 留在呈现层，调用方仅请求所需文字角色与尺寸；枚举、匹配和资源细节在内部处理。Game、solver、截图能力的读取、计算与 IO 执行面保持原约束。新增字体资产 IO、平台注册、渲染 Adapter 或 GUI 技术迁移均属于待批准设计取舍；涉及现有 ADR 范围变化时先形成 ADR 修订。

下一轮验证重点是：在 Linux 与 Windows 分别读回最终 family 和逐字符回退；比较正常、放大、最大化及连续缩放的字号、bbox 与页面观感；覆盖长提示、菜单与错误弹窗；验证输入命中、布局裁切和 ADR-005 要求的增量操作。现有 GUI 测试的断言已覆盖比例、提示面板重建及交互，字体质量和完整字形需要新增专项验证。Windows 运行事实、修复候选的真实渲染质量及原乱码位置对应关系仍待核验。上述路线均为研究建议，环境与架构变更由后续决策批准。
